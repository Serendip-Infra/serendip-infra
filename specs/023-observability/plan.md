# Plan 023: Observability — the observability-plane package

Status: Draft, 2026-11-11. Awaiting approval. Spec reviewed 2026-11-09
(a POC; three backends measured).

Upstream facts are in `research.md` (oss-researcher, 2026-11-09,
OpenChoreo v1.3.3). "Inferred" items there are checked by T001's spike.

> **Amended by T001 (2026-11-12):** Serendip queries OpenChoreo's
> **logs and metrics adapters** (the backend-neutral contract behind the
> Observer) through the API server's Service proxy, scoped by OpenChoreo
> IDs. It doesn't query the Observer: its public API needs a token even
> with security off. The plane object is a namespaced
> `ObservabilityPlane/default`. The node rule is built from live `Node`
> addresses, and uninstall deletes the namespace and the Prometheus
> Operator CRDs. See "Spike findings". Decisions 1, 4, 6 and 13 below
> are read with these amendments.

> **Amended by T003 (2026-11-14, ADR 0021):** the logs module is
> **logs-openobserve**, and metrics are **plain Prometheus**
> (`prometheus-community/prometheus` 29.47.2) with the metrics module
> installed for its adapter only (`kube-prometheus-stack.enabled=false`).
> No Prometheus Operator, no `monitoring.coreos.com` CRDs. The node rule
> is applied **before** the logs module's install. Decisions 1, 2, 3 and
> 13 are read with these amendments; see "Findings from T003".

## Approach in one paragraph

The package installs OpenChoreo's observability-plane chart (the
**Observer** and its agent and controller), one **logs module** and the
**metrics module**, and registers a namespaced `ObservabilityPlane/default`
in `openchoreo-control-plane`, which the existing data plane picks up by
name. Serendip asks the Observer
for logs and metrics through the Kubernetes API, behind a new
capability-shaped `ObservabilityProvider` in `core/`. The Observer's own
authentication stays off. Instead, NetworkPolicies close the Observer, the
stores and the adapters to everything but the collectors and Serendip's
path, so Serendip's RBAC stays the only gate (RP-018's pattern). Which
logs backend is used, and whether the Prometheus module is used as-is, is
settled by T001's measurement of three backends. The plan is written for
the Observer path, which holds for both of OpenChoreo's logs modules; a
SigNoz win would amend it (decision 2).

## Decisions

1. **What the package installs** (spec open questions 1, 3), in order,
   each checked:
   1. **The observability-plane chart 1.3.1** (ADR 0010's Helm path,
      matching the control plane),
      with:
      - `security.enabled=false` (decision 4);
      - `gateway.enabled=false`, since edge-1 already has a gateway and
        nothing outside the cluster needs the Observer;
      - RCA, FinOps and alerting's extras off (spec OUT);
      - the chart's own `networkPolicy` replaced by Serendip's
        (decision 4).
   2. **A logs module:** `observability-logs-openobserve` or
      `observability-logs-opensearch`, by T001. Either way it brings Fluent
      Bit as a DaemonSet, a logs adapter, a store and a setup job.
      - **Admin credentials** are generated by the installer and kept only
        in the module's Kubernetes Secret. They are never in Serendip's
        store or API, and are re-used on resync.
   3. **Metrics** (as amended by T003, decision 3): plain Prometheus
      (`prometheus-community/prometheus` 29.47.2, values from
      `profiles/edge-1/bench/observability-load/prometheus-plain-values.yaml`),
      then `observability-metrics-prometheus` 0.9.3 with
      `kube-prometheus-stack.enabled=false`, for its adapter. ~~The
      module as shipped, with Alertmanager off.~~
   4. **CA trust and `ObservabilityPlane/default`** (namespaced, in
      `openchoreo-control-plane`), hand-built
      with `providers/kubernetes.Client`, as for the workflow plane.
      - **The data plane isn't edited:** an omitted `observabilityPlaneRef`
        resolves to the CR named `default` (research). So removing the
        package doesn't touch the data plane's spec, and running Components
        aren't disturbed. T001 checks both.
   5. **Serendip's NetworkPolicies** (decision 4).

   All pinned in `providers/observability/openchoreo/VERSIONS.md`.

2. **The backend is chosen by T001's measurement; the leaning is
   OpenObserve** (spec open question 1, acceptance criterion 2).
   - **Measured on the simulated T470** (`bench-edge1`, same method as
     spec 022 T013: node-level use beyond the platform phase):
     - **A:** the plane chart, logs-opensearch (heap pinned at 512 MiB)
       and metrics-prometheus;
     - **B:** the plane chart, logs-openobserve and metrics-prometheus;
     - **C:** SigNoz 0.149.0 with its `k8s-infra` collector, on its own,
       for `capability-model.md`'s question.
   - **For each:** idle; under load (decision 9's generator for 30
     minutes); disk growth over 2 hours, extrapolated per day; the
     kube-apiserver delta (CRDs, RP-046); and whether the queries we need
     work (a text search, a CPU and memory range).
   - **Why the leaning:** OpenObserve requests 500 Mi against OpenSearch's
     JVM (about 1 GB in practice), needs no `vm.max_map_count` change on
     the node (OpenSearch does, which would be agent work), and covers
     traces later from the same instance.
   - **If SigNoz wins clearly,** it can't plug into the Observer. Using it
     would mean a SigNoz adapter in the provider, querying
     `/api/v5/query_range` with an API key. T001 records what that costs,
     and the user decides before T002.
   - **ADR 0021** records the choice with the numbers, and
     `capability-model.md` and `overview.md`'s open question is answered
     from the same table.

3. **The Prometheus Operator's CRDs are measured, with a fallback.** The
   metrics module installs kube-prometheus-stack's CRDs with no lighter
   option (research). Spec 022 found Argo's full CRDs held kube-apiserver
   about 550 MiB higher (RP-046).
   - **T001 measures the module as-is.**
   - **If its CRDs cost more than about 150 MiB at the node level,** the
     package installs plain Prometheus instead: the `prometheus`
     community chart, no operator, no CRDs, with a static scrape of the
     kubelet's cAdvisor endpoint. The module's metrics adapter is pointed
     at it. That's an amendment, recorded like spec 022's.
   - **As decided after T003 (ADR 0021):** the CRDs cost about 180 MiB
     (kube-apiserver and etcd) of the module's 647 MiB at idle, and
     kube-apiserver kept about 390 MiB after removal until restarted. So
     the fallback applies. Plain Prometheus with the adapter costs about
     134 MiB, and its queries work (B-plain in the T003 results).
     Prometheus is given the Service name and port the adapter fixes
     (`openchoreo-observability-prometheus:9091`), and kube-prometheus-
     stack's job names (`kubelet` for cAdvisor, `kube-state-metrics`),
     since the adapter's queries are written against those (RP-056).

4. **The query path** (spec open question 2, item 13).
   - **As decided after T001** (Spike findings 3–5, 9, 10 and 15):
     - Serendip queries the **logs and metrics adapters** through the API
       server's **Service proxy**, with UID scopes;
     - the Observer stays installed for the plane registration, but
       isn't queried;
     - the policies are the chart's own, plus a node rule built from
       live `Node` IPs.

     The rest of this decision is the pre-spike text, kept for the
     record, and is **superseded** where it differs.
   - **Why the Observer, not the backends' APIs:**
     - one query API for logs, build logs and metrics, whichever logs
       module is installed;
     - its scopes (project, component, environment; workflow run) match
       OpenChoreo's labels, which Serendip doesn't re-derive;
     - a backend swap is a module swap, not provider code.
   - **Why its authentication is off:** turning it on means a ThunderID
     client and token for `serendipd`, for a service no person reaches.
     Serendip's RBAC is the authority (ADR 0019), and the control plane
     already runs with security off behind a NetworkPolicy (RP-018).
   - **How Serendip reaches it:** through the API server, with
     `serendipd`'s own credentials. T001 picks one:
     - **port-forward** (`providers/kubernetes/portforward.go`), which
       enters the pod directly, so the policy can deny all other ingress;
       or
     - **the Service proxy** (`Client.ProxyURL`, as for OpenBao), which
       arrives from the node, so the policy must allow the node. Any
       `hostNetwork` pod could then reach the Observer, which T001
       records.

     Port-forward is preferred if it's reliable for short queries.
   - **Serendip's NetworkPolicies** (`serendip-deny-observability-*`,
     restored by the installer's checks, like RP-018's):
     - **The Observer, the adapters and the stores** accept ingress only
       from each other, the collectors that write to them, and Serendip's
       path.
     - **Fluent Bit** writes to the store. The OpenObserve module runs it
       with `hostNetwork`, so the store must allow the node, and T001
       records whether that can be narrowed.
   - **Acceptance criterion 9** is checked live from a workload pod
     against each of them.

5. **The capability's interface** (`core/reconcile/observability.go`, no
   product names):

   ```go
   type LogQuery struct {
       From, To time.Time // To zero means now
       Text     string    // plain phrase, not a query language
       Limit    int       // capped at 500
       Before   string    // opaque cursor from the previous page
   }
   type LogTarget struct { // one Component's logs in one Environment
       Deployment  resource.Deployment
       Component   resource.Component
       Environment resource.Environment
   }
   type StoredLogLine struct {
       Time      time.Time
       Component string // ID
       Instance  string // pod
       Container string
       Line      string
   }
   type LogPage struct { Lines []StoredLogLine; Next string; Truncated bool }
   type MetricsQuery struct { From, To time.Time; Step time.Duration }
   type Metrics struct {
       CPU, Memory      []MetricPoint // millicores, MiB
       CPURequest, CPULimit, MemoryRequest, MemoryLimit *float64
       Unavailable      []string // e.g. "requests", with the reason
   }
   type ObservabilityProvider interface {
       SearchLogs(ctx context.Context, targets []LogTarget, q LogQuery) (LogPage, error)
       BuildLogs(ctx context.Context, b resource.Build, q LogQuery) (LogPage, error)
       Metrics(ctx context.Context, t LogTarget, q MetricsQuery) (Metrics, error)
   }
   ```

   - **Registered under `observability`** once the package is Ready,
     through a lazy handle returning `ErrProviderNotReady` until then, the
     same as builds.
   - **Pagination** is by time: the cursor carries the oldest line's time
     and how many lines at that time were already returned. Lines are
     newest first.

6. **Scoping happens before the query** (spec open question 6, item 12).
   - **A Component's logs:** the route's rule checks
     `serendip/components/logs/read` on the Deployment, and the provider
     gets exactly that one target.
   - **An Application's logs in an Environment:** the route checks
     `serendip/applications/read` on the Application. The handler then
     lists the Application's Deployments in that Environment and keeps
     only those the caller holds `serendip/components/logs/read` on. Only
     those become targets.
     - **No allowed Deployment** is a 403.
     - **Some left out** is stated in the response (`omitted: n`) without
       naming them.
   - **The provider sends one Observer query per target** (component
     scope), merges them by time, and caps targets at 20 per request.
     Project-wide Observer queries are never sent, so a line the caller
     can't see is never fetched.
   - **Agents** go through the same checks with their own roles.

7. **Metrics are CPU and memory from the kubelet; HTTP is reported "not
   available"** (spec open question 5, item 8).
   - **CPU and memory** use the Observer's `metric=resource`
     (cAdvisor through Prometheus). Requests and limits come from the
     same response, or else from the Deployment's pods; anything missing
     is listed in `Unavailable`.
   - **Request rate, errors and latency** use `metric=http`. T001 checks
     where they come from. If they need Hubble or anything else not
     already installed, they're "not available: needs request metrics,
     not installed", and a later spec decides.
   - **Ranges:** from 15 minutes to the retention period. Step is chosen
     so a series has at most 300 points.

8. **Retention and disk are bounded and reported** (spec open question
   4, item 5).
   - **Defaults:** logs 3 days; metrics 3 days or 2 GiB, whichever comes
     first.
     - **Logs:** OpenObserve's data retention setting, or OpenSearch's
       `dataRetentionTime`.
     - **Metrics:** Prometheus' `retention` and `retentionSize`.
     - **Volumes:** logs 5 Gi, metrics 3 Gi, on local-path.
     - T001 confirms each setting works, and T013 measures the result.
   - **`provider.Requirements` gains an optional `Disk`:**
     `GrowthMiBPerDay`, `RetentionDays` and `BudgetMiB`, with
     `Validate` requiring all three when it's set. The catalogue states
     them, and the console shows "about N MiB a day, kept 3 days, at most
     M MiB".
   - **Current use:** an optional `PackageUsage` interface on an
     installer (`Usage(ctx) (DiskUsage, error)`), read from the kubelet's
     volume stats. `GET /v1/packages` includes it for an installed
     package, capped at one read per 30 s.
   - **Peak under load:** `Requirements.Peak*` is the cost under decision
     9's load, the same field builds uses for in-build.

9. **The load used for "under load"** (spec item 1):
   - five Components, each a pinned `busybox` writing 10 lines a second
     of about 120 bytes;
   - a log search across them every 10 s;
   - a 1-hour metrics query every 30 s.

   It's a manifest and a script in `profiles/edge-1/bench/`, so the
   numbers can be re-run on the real T470.

10. **Build logs after their pods are gone** (spec item 9). The build
    handler already reads a run's pods (spec 022). When they're gone ("logs
    expired") and observability is Ready, it asks
    `ObservabilityProvider.BuildLogs` instead. The Observer's
    workflow-run scope uses the Build's run name. Fluent Bit is a
    DaemonSet over every pod on the node, so build pods are collected with
    no workflow-plane change. Following a finished build isn't needed.
    Without observability, the route behaves as today.

11. **Routes and authorization:**

    | Route | Action (target) |
    |---|---|
    | `GET /v1/deployments/{id}/logs/search?q=&from=&to=&limit=&before=` | `serendip/components/logs/read` (Deployment) |
    | `GET /v1/applications/{id}/logs/search?environment=&...` | `serendip/applications/read` (Application), plus decision 6's check |
    | `GET /v1/deployments/{id}/metrics?from=&to=` | `serendip/observability/read` (Deployment) |
    | `GET /v1/builds/{id}/logs` | unchanged (`serendip/components/logs/read`) |

    - **`serendip/observability/read`** is a new action. Reader gets it
      through `*/read`; it isn't excluded the way logs are.
    - **Caps:** queries time out at 20 s; at most 3 at once per caller
      and 20 overall (spec 020's stream caps, RP-031); lines over 16 KiB
      are cut.
    - **Not ready:** 503 naming the package, as for builds.
    - **Reads aren't audited** (spec item 14). Install and removal are
      audited through the existing package path.
    - **`api/catalog`** gains each route, so the CLI commands
      (`serendip logs search`, `serendip metrics`) and MCP tools follow.
      The MCP metrics tool returns min, average, max and latest per series
      plus at most 60 points, so an assistant gets a summary.

12. **A cheap resync,** the same as builds (spec 022 decision 8).
    - **The fingerprint** covers three charts and their values, the
      `ObservabilityPlane` and the policies (including the nodes' IPs).
    - **When it's unchanged,** a few GETs check:
      - the Observer, the adapters, the store and Prometheus are ready;
      - the Fluent Bit DaemonSet is fully scheduled;
      - the CR exists;
      - the policies match.
    - **Installs and removals** run as package jobs (`packagejob.go`).

13. **Removal and its wording.**
    - **The catalogue's `removal`:** "All stored logs and metrics history
      are deleted. Recent logs and events on the Runtime tab keep working.
      Finished builds' logs can no longer be read once their pods are
      gone."
    - **Uninstall,** each step idempotent: the CR, the policies, the three
      Helm releases, and their PVCs and Secrets.
    - **CRDs the charts leave** are recorded, like RP-039.
    - **Builds** still works afterwards (spec item 6).

14. **No new Go dependency.** Everything new is stdlib: the Observer
    client, the charts through the existing Helm path, and the console's
    charts as inline SVG.

## Spike findings (T001, 2026-11-12, `serendip-t018`)

Config B installed by hand: the plane chart, logs-openobserve and
metrics-prometheus. Evidence is the command output in the session; the
numbers are `kubectl get --raw .../stats/summary` reads, not T003's
measurement.

1. **Versions.**
   - **Plane chart:** pinned at **1.3.1**, to match the control plane
     (1.3.3 exists).
   - **Modules:** logs-openobserve **0.8.0** (OpenObserve v0.92.2,
     Fluent Bit 5.1.5) and metrics-prometheus **0.9.3**
     (kube-prometheus-stack, 10 `monitoring.coreos.com` CRDs).
   - **Logs-opensearch:** 0.8.1, not installed yet (T003).
   - **Install time:** about 2 minutes for the plane, 2 for logs and 4
     for metrics.
2. **The plane chart needs more than its docs say:**
   - an `observer.secretName` Secret holding
     `UID_RESOLVER_OAUTH_CLIENT_SECRET`, even with security off (a
     placeholder works);
   - `observer.extraEnvs` overridden, because the chart refuses
     `.invalid` URLs;
   - **It doesn't create the plane CR.** Our namespaced `DataPlane`
     falls back to a namespaced **`ObservabilityPlane/default` in
     `openchoreo-control-plane`**, not the `ClusterObservabilityPlane`
     the research named. Serendip creates that object, and the
     `DataPlane`'s spec stays unedited (decision 1.4 amended).
3. **The Observer's public API can't be used without a token.** With
   `security.enabled=false`, JWT is off, but its authorization layer
   still answers 401 ("No subject context found"). It also calls
   `openchoreo-api`, which RP-018's policy closes. Its internal port
   (8081) has no query routes.
4. **The adapters are the query API** (decision 4 amended). Both answer
   without authentication, with the same request shape as the Observer:
   - logs: `POST logs-adapter:9098/api/v1/logs/query`;
   - metrics: `POST metrics-adapter:9099/api/v1/metrics/query`.

   They are OpenChoreo's backend-neutral contract
   (`openapi/observability-{logs,metrics}-adapter*.yaml`), so a logs
   module swap still needs no provider change.
5. **Scopes are IDs, not names, and an unknown or missing field widens
   the query silently.**
   - **Fields:** `searchScope{namespace, projectUid, componentUid,
     environmentUid}`. Names are ignored, and the query falls back to the
     whole OpenChoreo namespace. That's how a different Component and a
     nonexistent one each got the same 18 lines.
   - **With IDs, scoping is exact:** the right Component returns 18
     lines; another Component, or the right one in another Environment,
     returns 0. Metrics behave the same (A: 300 m requested, 22 MiB; B:
     100 m, 6 MiB).
   - **So the provider must:**
     - send the IDs (`metadata.uid` of the OpenChoreo `Component`,
       `Environment` and `Project`, which Serendip already reads);
     - refuse to send a scope with any ID missing;
     - drop any returned line whose `metadata.componentUid` or
       `environmentUid` isn't the target's (defence in depth).

     Decision 6 gains this.
6. **Search results** carry `level`, `log`, `timestamp` and `metadata`:
   component, environment and project names and IDs, `podName`,
   `podNamespace` and `containerName`.
   - **No cursor:** only `limit` (up to 1000) and the time window.
     Decision 5's cursor stays Serendip's own: the next page's `endTime`
     is the oldest line's time.
   - **About 50–60 ms per query** (20 queries through a port-forward:
     median 63 ms, max 125 ms).
7. **Metrics:** `resource` returns `cpuUsage`, `cpuRequests`,
   `cpuLimits`, `memoryUsage`, `memoryRequests` and `memoryLimits`
   (cAdvisor and kube-state-metrics). `http` returned `{}`; it needs
   Hubble's L7 metrics (research), so it's "not available" (decision 7
   confirmed).
8. **Upstream gap: the chart's policy blocks its own collector.**
   - The plane chart's `observability-plane-ingress` admits only pods in
     the namespace. Fluent Bit runs with `hostNetwork`, so every flush to
     OpenObserve timed out.
   - **Lines from that window were dropped** ("cannot be retried"), and
     the first marker was lost.
   - **Fix:** `serendip-allow-node-to-openobserve` admits the node's IP
     to OpenObserve's port 5080 only. OpenObserve's own credentials still
     apply.
   - **Risk:** logs written while the store is unreachable can be lost
     once Fluent Bit's retries run out (new RP).
   - `Read_from_Head On` re-reads every container log on the node at
     first install: 43,507 records in the first minutes.
9. **No side door.** From a pod in `default`, the Observer, both
   adapters, OpenObserve, Prometheus and kube-state-metrics all time
   out, while the same pod reaches `kubernetes.default` (200).
   - **A `hostNetwork` pod** can't reach the adapter either, by pod IP or
     ClusterIP.
   - **Open:** Fluent Bit's own `:2020` (`hostNetwork`, so outside any
     policy). It serves record counters only, no log content. Recorded;
     the chart's `HTTP_Server` could be turned off.
10. **The path from `serendipd`.**
    - **Port-forward** works through the policies.
    - **The Service proxy** (`/api/v1/namespaces/.../services/logs-adapter:9098/proxy/health`)
      answered too, in 0.19 s including `kubectl`'s start-up, even
      though a `hostNetwork` pod is blocked. kindnet admits the API
      server's proxy traffic.
    - **Decision 4: use the Service proxy,** the same as OpenBao:
      stateless, with no port-forward session to manage. K3s's
      behaviour is checked in T013, with port-forward as the fallback.
11. **Prometheus Operator CRDs:** kube-apiserver went 980 → 1148 MiB
    (+168 MiB) when the metrics module went in. That's over decision 3's
    150 MiB line, so **T003 measures the plain-Prometheus fallback**.
12. **Footprint, rough** (pods' working set, about 10 minutes in):
    - **Total:** 316 MiB and 37 mcores. That's OpenObserve 117,
      Prometheus 112, the operator 18, and 8–12 each for the controller,
      the Observer, kube-state-metrics, Fluent Bit, both adapters and the
      agent.
    - **The node** went 2469 → 3344 MiB, including the CRDs and cache.
    - **The Observer, its agent and the controller (about 30 MiB)** are
      kept for the plane registration; whether they can go is a T003
      question.
14. **Retention is settable and applied.**
    - **Logs:** `openobserve-standalone.config.ZO_COMPACT_DATA_RETENTION_DAYS=3`
      reaches the `openobserve` ConfigMap. The module's default is
      **3650 days**, so the package must always set it.
    - **Metrics:** Prometheus `retention: 3d`, `retentionSize: 2GiB`.
    - **Volumes:** 5Gi and 3Gi bound on `standard` (local-path). Whether
      deletion actually happens at the limit is T012's disk run.
15. **A node IP change breaks a pinned node rule.**
    - Docker Desktop restarted overnight, and the kind node came back as
      172.22.0.5 (was .2). Fluent Bit's flushes timed out, and lines were
      dropped again, until the rule was rebuilt from the `Node` objects'
      `InternalIP`s. Then 36 successful flushes in 20 s.
    - **Decision 4 amended:** the installer builds the node rule from
      the current `Node` addresses, and the resync check compares them,
      so a changed IP is repaired within one resync.
    - **Not an option:** Fluent Bit off the host network. The module
      hardcodes `Use_Kubelet true`.
    - Also seen after the restart: the adapters, kube-state-metrics and
      Fluent Bit crash-looped for about 2 minutes, until OpenObserve and
      Prometheus were up, then settled with no action. The readiness
      checks must tolerate this.
16. **Removal** (decision 13's order: the CR, Serendip's policy, then the
    three Helm releases), done in 5 s.
    - **The data plane** was unchanged (same generation and spec), and
      the running Components kept serving (200 from inside a pod).
    - **Helm left behind:**
      - both PVCs;
      - the Secrets `cluster-agent-tls`, `observer-secret`,
        `openobserve-admin-credentials` and
        `openchoreo-observability-admission`;
      - the `cluster-gateway-ca` ConfigMap;
      - a completed setup-job pod;
      - **10 `monitoring.coreos.com` CRDs** and the plane chart's
        `observabilityalertrules` CRD.
    - **Decision 13 amended:** uninstall deletes the namespace, which
      covers PVCs, Secrets and the job, and deletes the Prometheus
      Operator CRDs if the metrics module is kept. Left installed, they
      hold kube-apiserver's 168 MiB after removal. The plane chart's
      alert-rule CRD is small and is left, as RP-039 left Argo's.
    - **Clean-up done:** the namespace, the CRDs and the test pods are
      gone; `kubectl get crd` shows no `monitoring.coreos.com` or
      `observabilityalertrules`.
17. **Not testable here:** build-log scope. The builds package was
    removed in spec 022 T014. The research gives the adapter's mapping:
    `kubernetes_namespace_name='workflows-<ns>'` and the label
    `workflows.argoproj.io/workflow=<run>`. T013 checks it with builds
    installed.

## Finding from T002 (2026-11-12): the kubelet doesn't measure local-path volumes

- The kubelet Summary API reports no usage for hostPath-backed
  PersistentVolumes, which is what local-path provisions.
  - On `serendip-t018` none of the four local-path PVCs (OpenBao's and
    ThunderID's) had a `pvcRef` entry.
  - It does for CSI volumes such as Longhorn's.
- **The bench** measures them with a short-lived `du` probe pod at each
  phase's start and end (`cmd/bench-edge1/disk.go`).
- **Decision 8 amended:** the package's *current disk use* can't come
  from the kubelet's volume stats on edge-1. `Usage` asks the stores
  instead:
  - OpenObserve's stream stats (`/api/{org}/streams`, `storage_size`,
    seen in T001);
  - Prometheus' own `prometheus_tsdb_storage_blocks_bytes` plus its WAL
    size.

  T006 settles the exact calls. A `du` from Serendip would mean exec
  into a pod or a privileged probe, which the product shouldn't need.

## Finding during T003 (2026-11-12): telemetry and downloads

- **OpenObserve phones home by default.** `openobserve-standalone` sets
  `ZO_TELEMETRY: "true"`, a heartbeat every 1800 s to
  `https://e1.zinclabs.dev`. SigNoz also enables telemetry by default.
  - **Decision 1 gains:** the installer sets `ZO_TELEMETRY=false`. No
    package may send anything off the machine unless asked; edge-1
    must work offline.
  - T005 checks the values, and T013 checks that no connection leaves
    the node.
- **Internet use is image pulls at install only:**
  - the edge-1 platform is about 550 MB (measured on the new
    `bench-t470` node);
  - each backend's pull size is recorded in T003's results.
  - Removing and reinstalling on the same node pulls nothing again.

## Findings from T003 (2026-11-12 to 2026-11-14, `bench-t470`)

The measurements and the choice are in ADR 0021. What the installer
(T005) must do differently:

1. **The node rule goes in before the logs module's install.**
   logs-opensearch's Fluent Bit has an init container that waits for the
   store's index template; with the rule applied after `--wait`, the
   install can never finish. OpenObserve's Fluent Bit has no such wait,
   but the same order is used for both.
2. **Generated passwords need a symbol, a digit and both cases.**
   OpenObserve crash-looped on a long alphanumeric one ("too weak").
3. **The install has a long first start.** OpenSearch took about
   13 minutes to start the first time (the image pull and the deadlock
   in 1); 169 s once both were fixed. The installer's timeouts allow for
   the first pull.
4. **Removing the metrics module's CRDs doesn't return kube-apiserver's
   memory** (about 390 MiB) until it restarts. Plain Prometheus avoids
   this; it is why decision 3's fallback applies.
5. **SigNoz, for the record** (not adopted, ADR 0021):
   - it ingests nothing until a root user creates its organization;
   - its stats reporter is on by default;
   - its ClickHouse object must be deleted before its operator, or the
     namespace hangs;
   - k8s-infra needs a full `http://` OTLP URL.
6. **A mid-run bench fix:** `load.sh` dropped the driver's `--env` flags
   (its `--overrides` replace the container). It only affected C's first
   minute of load, which is noted in C's results.
7. **Not measured: 30 minutes of load.** Every config ran a 10-minute load
   phase and then stayed under load through its disk phase: 2 hours for
   B, 1 hour for A and C. So every config had at least 70 minutes under
   load.

## Findings from T005 (2026-11-14): the installer

The charts were rendered with `helm template` at the pinned versions, and
the digests match `VERSIONS.md`. What the installer does differently from
the decisions above:

1. **The nodes' addresses aren't in the fingerprint** (decision 12). They
   change without any install. So the fingerprint stays static, and the
   check compares the live rule with the current `Node` addresses. A
   change is repaired by re-applying the rule, with no Helm run. IPv6
   addresses get `/128`.
2. **"The policies match"** means:
   - the plane chart's `observability-plane-ingress` exists (if not, the
     plane chart is re-run);
   - Serendip's rule exists with the current addresses;
   - a ready pod matches the rule's selector. The logs store's readiness
     check uses the same selector.
3. **The readiness query's "known pod"** is the longest-running ready pod
   carrying all four OpenChoreo scope labels (namespace, project,
   component and environment UIDs), started at least 5 minutes ago. The
   query asks the adapter for the last 10 minutes through the Service
   proxy.
   - **With no such pod,** the package is Ready, and its message says
     metrics are checked once a Component has run that long.
   - **Empty series** are reported and not repaired, because re-running
     Helm can't fix a mismatch (RP-056).
   - **An error answer** settles, then re-runs only the metrics module.
   - **Cost:** the chosen pod is remembered and read back by name, one
     small GET. The cluster-wide list (filtered by label and phase) runs
     only on the first check after a start, or when that pod is gone or
     no longer eligible. So a resync costs the same however many
     Components run.
4. **The agent's connection isn't checked.** Unlike the workflow plane,
   `ObservabilityPlane`'s status shape wasn't recorded in T001. Nothing
   Serendip queries goes through the agent, so the object only has to
   exist. T013 records its status.
5. **After a restart,** the first resync that finds the package applied
   starts one settle window, so a rebooted node's pods coming up are
   waited out rather than met with a 15-minute Helm run.
6. **Uninstall waits for `ObservabilityPlane/default` to be gone** before
   removing the plane's controller, so a finalizer can't leave it stuck
   in `openchoreo-control-plane`.
7. **The admin Secret** is created once and never replaced. An existing
   one missing a key stops the install with a message, since the store's
   data was written under the credentials it had.
8. **The logs module renders an `HTTPRoute`** for remote Fluent Bit,
   attached to `gateway-default` in the plane's namespace. With the
   plane's gateway off, that gateway doesn't exist, so the route attaches
   to nothing.
9. **The Prometheus values are embedded** (`prometheus-values.yaml`), and
   a test keeps them identical to the bench's file.
10. **Proxy requests carry the bearer token.** `kubernetes.Client.PostRaw`
    sends requests through the client's own credentials, including a
    bearer token. `HTTPClient()` alone doesn't add the token (RP-057).

## Findings from T006 (2026-11-14): the client and the provider

The adapters' OpenAPI at v1.3.1 and the community modules' adapter code
were read through the `oss-researcher`. Tested on an `httptest` fake
only; the first live queries are T012's.

1. **The scope is resolved from the live objects.** The provider repeats
   the application provider's name derivation (`cmp-`, `env-` and the
   Component's `spec.owner.projectName`) and reads each object's
   `metadata.uid`. `kubernetes.ObjectMeta` gained `UID`. Resolved UIDs
   are cached for a minute, and missing objects for 5 s, so a 20-target
   search doesn't cost 60 GETs every time.
   - **A target must hang together:** the Deployment runs the Component
     and is owned by the Environment, or the search is refused. A target
     given twice is read once.
   - **Returned lines are checked** against all three UIDs (component,
     environment and project).
   - **A target whose objects are gone is skipped,** never widened. For
     metrics it's reported unavailable.
   - **A re-created object hides its predecessor's logs** (RP-059).
2. **The two scopes are told apart by `workflowRunName`.** The schema's
   `oneOf` has no discriminator; the adapter treats a request as a build
   run's when that field is set. A build's scope sends the OpenChoreo
   namespace (`serendip-builds`); the adapter adds `workflows-` itself.
   A build-run line carries only its time and text, so `Instance` is
   empty. Argo's own lines are dropped, as the build provider does.
3. **Paging** (decision 5's cursor, RP-058):
   - the adapters accept at most 1000 lines (not enforced by the
     OpenObserve adapter, so enforced here), sort with no tiebreak, and
     keep microseconds;
   - whether the end bound is inclusive isn't known, so the query asks
     for a microsecond more and drops anything newer;
   - each round asks every target for the rest of the page, plus the
     lines the cursor skips, plus one. A target that answered in full
     isn't trusted below its oldest line, so the next round starts
     there (at most 4 rounds a page). A target that answered less has
     sent everything and isn't asked again. Ties keep the targets' order;
   - a page can be short, even empty, with `Next` set (noted on
     `LogPage`), so only an empty `Next` ends a search;
   - lines are cut to 16 KiB as they're read. An answer over the
     client's 8 MiB cap is asked again for half as many lines
     (`kubernetes.ErrBodyTooLarge`);
   - a future `To` is clamped to now. One failing target fails the page,
     and stops the others' queries.
4. **Metrics units:** the adapter answers cores and bytes; the provider
   gives millicores and MiB. Requests and limits are series too; the
   latest point is used. Step is whole minutes (at least the 1-minute
   scrape), so a range has at most 300 points. `http` is never queried.
5. **Disk use (decision 8 as amended by T002), as checked live:**
   - **OpenObserve:** its streams API (`/api/default/streams?type=logs`),
     `compressed_size` plus `index_size`, summed over streams. The sizes
     are **MiB**: on `serendip-t018` the two came to exactly the bytes of
     the files in `stream/` (515,798), and `compressed_size` alone to
     exactly its Parquet files (310,281).
     - **Its `/metrics` has no stored-size gauge** at v0.92.2 (the
       `storage_*` names are a later version's), and `zo_node_disk_*` is
       the whole host disk. So the earlier plan, `/metrics` with no
       credentials, was dropped, with its `ZO_PROMETHEUS_ENABLED=true`.
     - **The API needs the admin credentials, and kube-apiserver's
       Service proxy strips an `Authorization` header** (401 through the
       proxy, 200 direct with the same credentials). So the request goes
       over a port-forward (`ServiceDialer`) to the store's pod. The
       credentials are read from the Secret for each read and never kept.
     - **The stats lag** (synced every 10 minutes) and leave out the
       write-ahead log and the metadata database (RP-061).
   - **Prometheus:** `prometheus_tsdb_storage_blocks_bytes` plus
     `prometheus_tsdb_wal_storage_size_bytes` from its `/metrics` through
     the Service proxy (checked live; no credentials).

   A field or metric that's missing is an error, not zero. Read at most
   once per 30 s, and a failed read is kept for the same 30 s.

6. **Checked live on `serendip-t018`** (`live_test.go`, opt-in through
   `OBS_LIVE_KUBECONFIG`; it installed, removed and re-installed the
   package through the real installer):
   - **Install** in under 3 minutes; **Uninstall** in 38 s, leaving no
     namespace, plane object or Prometheus Operator CRDs.
   - **Scopes** from real Serendip IDs (spec 022 T014's store): 3 of 3
     Deployments, UIDs equal to their pods' labels.
   - **The answer shapes** are the OpenAPI's, `projectUid` included.
   - **The end bound is exclusive**: a line at exactly `endTime` isn't
     returned. The query's extra microsecond covers it.
   - **Paging:** 75 lines paged by 7 equal one 500-line page, line for
     line (18 after the re-install).
   - **Metrics units:** a CPU request of 0.1 core came back as 100 m and
     268435456 bytes as 256 MiB, matching the pod spec; CPU usage
     appears once Prometheus has 2 minutes of data (a `rate` over 2m).
   - **Build logs:** a stand-in step pod with the run's namespace and
     Argo's workflow label gave its 25 lines, with Argo's own line
     dropped. A real build's pods carry that label (spec 022 T001).
   - **OpenObserve called out even with telemetry off**: GeoLite
     databases from `geoip.zinclabs.dev` (60 MB, refreshed every 30
     days) and LLM pricing from `raw.githubusercontent.com`. The
     installer now sets `ZO_MMDB_DISABLE_DOWNLOAD=true` (a config key)
     and `ZO_MODEL_PRICING_ENABLED=false` (not a key the chart renders,
     so through `extraEnv`). After a fresh install, its log names no
     outside URL and no `mmdb` folder exists.
   - **A store no Component has written to** has none of the label
     fields, so a scoped search answers a bare 500 (OpenObserve: "unknown
     field"). The error now says what it may mean.
   - **The first resync after an install** comes before Prometheus'
     first scrape; inside the settle window it now says it's waiting for
     the first metrics, rather than warning of a mismatch.
   - **Fluent Bit's read positions** stay on the node after removal
     (RP-060).

7. **Reviews:** `go-reviewer`'s findings are fixed, except one left as
   is: scopes are resolved one target after another, since they're cached
   and a first search's GETs (at most 60) stay on the local API server.
   `contract-guardian` passed.

## Risks

- **Weight.** Three charts and a store on 2 cores and 16 GB. The cost is
  stated before install, and the package stays optional. If even the
  lighter backend doesn't fit comfortably, the catalogue says so (spec
  item 2).
- **The Prometheus Operator's CRDs** may cost more than all the pods
  (RP-046). Decision 3's fallback covers it.
- **The Observer's authentication is off.** Its safety rests on the
  NetworkPolicies and on Cilium or kindnet enforcing them.
  - Same residual risk as RP-018: policies match by label, so a relabel
    in a future chart re-opens them. The checks verify each selector
    matches a pod.
  - K3s enforcement still needs verifying live (RP-018's open item).
- **`hostNetwork` Fluent Bit** forces the store to accept traffic from
  the node, so any `hostNetwork` pod can write logs, or read them if the
  store's own credentials leak.
- **Logs keep what pods print, secrets included,** for 3 days. That's why
  stored logs need Log Reader, the same as pod logs.
- **Disk.** A noisy Component could fill the logs volume before retention
  acts. The size caps bound it, and the package reports current use.
- **Community modules move faster than the core charts.** They're
  pinned, and the modules' versions and compatibility are noted in
  `VERSIONS.md`.
- **Unconfirmed upstream behaviour:**
  - whether the Observer resolves component scopes with security off
    (it has a UID resolver that normally uses an OAuth client);
  - whether the plane chart creates the CR itself.

  T001 checks both. If the resolver fails, the provider passes namespace
  scopes it builds itself, from the same labels the runtime view uses.
- **Pagination by time** can repeat or skip lines with identical
  timestamps beyond the cursor's count. This is low risk and recorded.
